# Fincode — CRM и Service Desk

Корпоративное приложение Fincode по ТЗ `Fincode_CRM_Service_Desk_TZ.md`
(оболочка), `Fincode_CRM_Kanban_TZ.md` (канбан сделок) и
`Fincode_CRM_Clients_TZ.md` (верхнее меню и справочник клиентов).

- Боковое меню с двумя разделами (`CRM`, `Service Desk`), верхняя панель,
  переключатель светлой и тёмной темы с сохранением выбора, фирменный отпечаток.
- CRM: верхнее меню «Сделки» / «Клиенты» / «Поставщики».
  - «Сделки» — прежний канбан из семи столбцов с суммой `0 BYN` под названием.
  - «Клиенты» — таблица клиентов из базы, поиск по ФИО и создание клиента
    в модальном окне. Данные сохраняются на сервере (SQLite) и переживают
    обновление страницы.
  - «Поставщики» — пустая рабочая область.
- Service Desk не изменён: пустая рабочая область без канбана и клиентов.

Форма создания сделки, карточки, перетаскивание и серверный расчёт сумм канбана
в эту версию не входят (см. «Реализовано и отложено»).

## Стек

- React 19 + TypeScript, сборка Vite.
- `react-router-dom` (BrowserRouter): `/crm/deals`, `/crm/clients`,
  `/crm/suppliers`, `/service-desk`; `/crm` и `/` ведут на `/crm/deals`.
- Стили — обычный CSS с токенами в `src/styles/tokens.css`, без UI-библиотек.
- Сервер — Node.js без внешних зависимостей (`node:http`), база — SQLite через
  встроенный модуль `node:sqlite`. Отдельного сервера БД не требуется.
- Графика хранится локально в `public/assets/brand`, внешних URL нет.

## Требования

Node.js 22.5 или новее (нужен модуль `node:sqlite`). Проверено на Node 26.13.1,
npm 11.20.0. Внешние сервисы и установка СУБД не нужны.

## Запуск

```bash
npm install       # установка зависимостей
npm run dev       # разработка: API на :3001 + Vite на http://localhost:5173
npm run build     # проверка типов + production-сборка в dist/
npm run start     # production: API и собранный SPA на http://localhost:4173
npm run migrate   # применение миграций базы (выполняется и при старте сервера)
```

`npm run dev` поднимает API-сервер и dev-сервер Vite в одном процессе
(`tools/dev.mjs`); запросы `/api/*` проксируются с `:5173` на `:3001`
(`server.proxy` в `vite.config.ts`).

`npm run start` (он же `npm run preview`) запускает `server/index.mjs`: он отдаёт
собранный SPA из `dist/` и API, поэтому клиенты работают и в production.
Оба сервера отдают `index.html` для любого пути (`appType: 'spa'`), поэтому
прямые ссылки и обновление страницы работают без дополнительной настройки.

Пути и порты настраиваются переменными окружения:

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `PORT` | порт сервера приложения | `4173` |
| `HOST` | интерфейс прослушивания | `127.0.0.1` |
| `FINCODE_DB` | файл базы данных SQLite | `data/fincode.db` |
| `STATIC_DIR` | каталог сборки для раздачи | `dist` |

### Публикация

Отдельный статический хостинг не нужен: `npm run start` уже отдаёт и SPA, и API.
Если приложение разносится на статический хостинг и API, статике всё равно нужен
fallback на `index.html` для клиентских маршрутов. Пример для nginx:

```nginx
location / {
  try_files $uri $uri/ /index.html;
}
location /api/ {
  proxy_pass http://127.0.0.1:4173;
}
```

## База данных и серверный API

Данные клиентов хранятся в SQLite (`node:sqlite`, файл `data/fincode.db`,
создаётся автоматически). Миграции лежат в `server/migrations/` и применяются
при старте сервера и командой `npm run migrate`; повторный запуск ничего не
пересоздаёт и не удаляет существующие записи (используется `CREATE TABLE IF NOT
EXISTS`, применённые файлы отмечаются в `schema_migrations`).

### Соответствие формы, API и таблицы «Клиенты»

Бизнес-таблица «Клиенты» называется `clients` (латиницей, как принято в проекте).

| Поле формы | Поле API | Колонка `clients` | Тип и ограничение |
|---|---|---|---|
| Фамилия | `last_name` | `last_name` | `TEXT NULL`, до 100 символов |
| Имя | `first_name` | `first_name` | `TEXT NOT NULL`, не пустая строка после trim, до 100 |
| Отчество | `middle_name` | `middle_name` | `TEXT NULL`, до 100 |
| Телефон | `phone` | `phone` | `TEXT NOT NULL`, не пустая строка после trim, до 50 |
| E-mail | `email` | `email` | `TEXT NULL`, до 254 |
| Ответственный | `responsible_user_id` | `responsible_user_id` | `TEXT NOT NULL`, внешний ключ на `users(id)` |

Дополнительно в `clients` есть `id` (первичный ключ, UUID, задаёт сервер),
`created_at` и `updated_at` (ISO-8601, задаёт сервер). Пустые необязательные
поля хранятся как `NULL`, а не как строки `"null"` или пустая строка.
Отображаемое ФИО формируется из частей, отдельного дублирующего поля нет.

Справочник ответственных — таблица `users`. Устойчивый идентификатор записи
Минича Антона Андреевича — `usr-minich-anton-andreevich`; запись создаётся один
раз миграцией (`INSERT OR IGNORE`), новые пользователи при создании клиента не
создаются. Клиент хранит идентификатор пользователя, а не текст его ФИО.

### API

| Метод и путь | Назначение |
|---|---|
| `GET /api/clients?search=&page=1&pageSize=50` | список клиентов с поиском по ФИО и пагинацией |
| `POST /api/clients` | создание клиента, ответ `201` с созданным объектом |
| `GET /api/users?selectableAsResponsible=true` | справочник ответственных |
| `GET /api/health` | проверка доступности сервера |

Ответ списка: `{ items, total, page, pageSize, hasMore }`; каждая запись
содержит ФИО ответственного (`responsible_full_name`), поэтому отдельные запросы
на строку не нужны. Ошибка проверки полей — `422` с
`error.fieldErrors` по полям формы; внутренние ошибки базы наружу не выводятся.

Поиск выполняется на сервере по всему набору клиентов, а не по загруженной
странице. Сравнение регистронезависимо для кириллицы (`toLocaleLowerCase('ru')`):
встроенные `lower()`/`LIKE` в SQLite не понижают регистр кириллицы без ICU.
Запрос разбивается на слова; каждое слово должно найтись в ФИО, порядок слов не
важен. Пагинация применяется после отбора, поэтому поиск не теряет записи за
пределами первой страницы.

### Защита от повторного создания

Клиент отправляет заголовок `Idempotency-Key` (UUID, создаётся при открытии
формы и сохраняется для повторных попыток). Сервер хранит ответ первого
успешного запроса в таблице `client_creation_requests` и при повторе того же
ключа возвращает ту же запись с заголовком `Idempotent-Replay: true`, не создавая
вторую строку. Вставка клиента и запись ключа выполняются в одной транзакции.
Кнопка «Создать» дополнительно блокируется на время запроса («Сохранение…»),
поэтому двойное нажатие отправляет один запрос.

## Токены и поведение

- Палитра, размеры и отступы вынесены в `src/styles/tokens.css`. Значения
  `--bg-workspace`, `--bg-sidebar`, `--text-primary`, `--text-muted`, `--border`,
  `--nav-active-bg`, `--nav-active-text`, `--switch-on` взяты из раздела 8.2 ТЗ.
  Дополнительно добавлены производные токены для состояний: `--nav-hover-bg`,
  `--switch-off`, `--switch-knob`, `--focus-ring`.
- `--text-muted` в светлой теме скорректирован с `#81899C` до `#667085`:
  исходное значение даёт контраст 3.5:1 на белом фоне, что ниже требуемых 4.5:1.
  Новое значение сохраняет оттенок и даёт 4.97:1 на панели и 4.61:1 на рабочей
  области.
- Тема хранится в `localStorage` под ключом `fincode-theme` (`light` / `dark`),
  по умолчанию — светлая. Инлайн-скрипт в `index.html` применяет тему до первого
  отображения, поэтому вспышки светлого фона нет. При недоступном `localStorage`
  интерфейс продолжает работать, сохранение между сеансами не гарантируется.
- Тема задаётся атрибутом `data-theme` на `<html>` и `color-scheme`; логотип и
  декоративный отпечаток переключаются вместе с палитрой.
- Активный пункт меню помечается `aria-current="page"` (проставляет `NavLink`).
- Переключатель темы — `role="switch"` с `aria-checked`, доступное имя
  «Тёмная тема», кликабельна вся строка.
- Декор: `aria-hidden`, пустой `alt`, `pointer-events: none`, `user-select: none`,
  без анимации; рабочая область обрезает его по своим границам, поэтому прокрутка
  не появляется. Отпечаток один и тот же в обеих темах, отличается только
  непрозрачность (`--decor-opacity`: 0.30 в светлой, 0.55 в тёмной) и смещение
  (`--decor-right`, `--decor-bottom`).
- Добавлены токены нового интерфейса: вкладок CRM (`--crm-tabs-*`, `--crm-tab-*`),
  поля и таблицы клиентов (`--search-width`, `--field-*`, `--table-*`),
  модального окна (`--modal-*`, `--modal-backdrop`), уведомления (`--toast-offset`)
  и текста ошибок (`--error-text`: `#b04040` в светлой теме, `#f2a0a0` в тёмной;
  контраст на поверхности не ниже 4.5:1). Цвет подчёркивания активной вкладки —
  `#25ada2`, как в макете. Фон таблицы, полей и окна берётся из `--surface`
  (`#ffffff` / `#0d1633`), поэтому тёмная тема не требует отдельных правил.
- Вкладки CRM — навигационные ссылки в `<nav aria-label="Разделы CRM">`; активная
  получает `aria-current="page"` и класс `crm-tab--active`. Это второй
  `aria-current` на странице после бокового меню, поэтому проверки считают
  активные элементы отдельно в `.sidebar__nav` и в `.crm-tabs`.
- Модальное окно — нативный `<dialog>`: фокус остаётся внутри окна, Escape
  перехватывается и подчиняется правилам закрытия из раздела 10 ТЗ, клик по
  подложке окно не закрывает.

### Телефон клиента

Дополнение к `Fincode_CRM_Clients_TZ.md`: маска с постоянным префиксом `+375`.

- **Формат.** Вводится только национальная часть — 9 цифр (код 2 цифры и номер
  7 цифр). Отображение: `+375 (XX) XXX-XX-XX`, подсказка в пустом поле
  `+375 (__) ___-__-__`. Атрибуты поля: `type="tel"`, `inputmode="tel"`,
  `autocomplete="tel"`. Принимаются только цифры, сверх девяти ввод не
  принимается, знаки оформления расставляются автоматически.
- **Backspace** удаляет цифру вместе со знаками оформления: `+375 (44) 757-40-55`
  → `+375 (44) 757-40-5` → `+375 (44) 757-40`.
- **Вставка из буфера** приводит текст к девяти цифрам национальной части:
  распознаются начала `+375`, `375`, `80` и «8 0». Например, `8 044 757-40-55`,
  `+375447574055`, `375447574055`, `80447574055` и `+375 (44) 757-40-55` дают
  `+375 (44) 757-40-55`; лишние цифры отбрасываются с конца.
- **Допустимые коды:** 17, 25, 29, 33, 44. Список вынесен в
  `config/phone-national-codes.json` — этот же файл читает сервер
  (`server/phone.mjs`), поэтому форма и сервер используют один список.
- **Ошибки** появляются после потери фокуса или при попытке сохранить, а не на
  первой цифре: «Укажите телефон» (пусто или только `+375`), «Введите номер
  полностью: +375 (XX) XXX-XX-XX» (меньше 9 цифр), «Укажите номер с кодом 17, 25,
  29, 33 или 44» (код вне списка). Сообщение о коде собирается из списка, чтобы не
  расходиться с ним.
- **Хранение.** В форме и списке — `+375 (XX) XXX-XX-XX`, в базе и API —
  `+375XXXXXXXXX` ровно 13 символов, без пробелов, скобок и дефисов. Сервер
  нормализует телефон по тем же правилам и отклоняет неверный номер даже в обход
  формы (422 с сообщением у поля `phone`). Форматирование выполняется только при
  выводе.
- **Префикс `+375`** в пустом поле пользовательским изменением не считается:
  подтверждение «Закрыть окно без сохранения?» из-за него не показывается.
- **Старые записи** в другом формате интерфейс показывает как есть, без миграции.
  В рабочей базе на момент доработки одна такая запись: `=375441203343`
  (13 символов, префикс `=` вместо `+`, без разделителей); остальные записи уже
  соответствуют `+375XXXXXXXXX`.

Доработка по `Fincode_CRM_Clients_Design_Update_TZ.md` — только визуальная:
поля формы, поиск, проверки, сортировка, пагинация и серверная логика не менялись.

- **Полупрозрачная поверхность таблицы.** Контейнер залит `rgba(255, 255, 255,

## Известные ограничения

- Маршрутизация клиентская. Для production нужен fallback сервера на
  `index.html` (пример для nginx выше); при открытии `dist/index.html` напрямую
  через `file://` маршруты не работают.
- Светлая тема — последняя предложенная редакция, отдельного визуального
  согласования заказчика нет. Тёмная тема воспроизведена по согласованному
  референсу и при правках светлой не меняется.
- Отпечаток в обеих темах — один и тот же чистый знак из логотипа, без бликов,
  свечения и тёмной подложки референса. Непрозрачность: 0.30 в светлой теме,
  0.55 в тёмной. Это отступление от раздела 7.2 ТЗ (там для тёмной темы
  предполагался правый нижний фрагмент референса) — сделано по решению заказчика.
- Смещение декора задано по разделу 7 ТЗ: в светлой теме отпечаток частично
  выходит за край области (`right: -85px`, `bottom: -125px`), в тёмной прижат к
  правому нижнему углу (`right: 0`, `bottom: 0`).
- Авторизации и ролей нет: `АМ` — заглушка. Проверки доступа к API не применяются
  до появления системы авторизации (модель ролей в ТЗ на клиентов не определяется).
- Проверено в Chromium, Firefox и WebKit (движок Safari) на размерах
  1800 × 1000, 1440 × 900, 1280 × 800, 1024 × 768, 768 × 1024 и 390 × 844.
- На узких настольных ширинах семь столбцов при минимальной ширине 174 px не
  помещаются целиком, поэтому доска прокручивается по горизонтали (раздел 5 ТЗ).
  Без прокрутки все семь столбцов видны от ~1610 px окна (например, 1800 px).
- Поиск клиентов отбирает записи в приложении на сервере, а не в SQL: `LIKE`
  в SQLite без ICU не понижает регистр кириллицы. Для заявленного объёма
  справочника это достаточно; при росте данных стоит вынести нормализованное
  поле поиска в базу.
- Пагинация клиентов — по 50 записей, догрузка кнопкой «Показать ещё».
